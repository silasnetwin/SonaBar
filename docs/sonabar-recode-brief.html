03 · Die Vorlage

Das „komische Fenster“ ist eigentlich gut.

Die Optik ist Tkinter/Win32, nicht das Ziel. Das Informationsmodell ist das Ziel.

Übernehmen

Status-first: „Ready / Listening / Transcribing“ als größtes Element. Eine Zeile Kontext: Mode, Hotkey, Model. Letzte Transkription bleibt sichtbar. Settings als Dialog mit Provider, Modell, CPU, Threads, Min Hold.

Nicht übernehmen

Kein Tkinter-Look, keine fehlende DPI-/Screenreader-Unterstützung, keine versteckten Provider, keine Modell-Downloads ohne SHA-256, kein „Ready“, das nicht wirklich bereit ist. SonaBar bleibt WPF mit Themes, High Contrast und echten Zuständen.

Die Formel

Ein Fenster, eine Aufgabe: bereit sein, zuhören, Text liefern. Alles andere — Files, Meetings, History, Snippets, Writing, Apps — lebt hinter „Open workspace“. Kein Feature wird entfernt, nur priorisiert.

Schon gut

Parakeet TDT v3 ist bereits eingebunden und CPU-verifiziert. Whisper, Qwen, History, Snippets, Typed Expansion, Updates und Qwen-Sidecar sind vorhanden. SonaBar muss die Engine nicht erfinden.

Wirklich neu

Compact-Shell, Settings-Dialog, echte CPU/Thread-Wahl, Min Hold, Hotword-Brücke, optionaler deutscher Parakeet-Fine-Tune. Das ist genug für einen großen Schnitt — aber kein Grund, die Logik neu zu schreiben.

Nicht anfassen

05 · Umsetzung

Fünf Phasen, ein Produkt.

Die Reihenfolge ist wichtig: Erst messen und die Wahrheit in die Einstellungen bringen, dann die Shell umbauen, dann das Modell evaluieren. Nicht mit dem schönsten Screenshot anfangen.

Baseline messen & guardrails

Fixierte WAVs (2 s, 5 s, 10 s, 30 s), drei Runs, P50/P95 für Key-Release → Insert. Whisper small/turbo, Parakeet v3, Qwen ASR. RAM, VRAM, Threads, Modell-Ladezeit. Keine UI-Änderung.

# ZIEL
Baue SonaBar von einer großen Multi-Page-Workspace-App zu einer kompakten Windows-Diktierutility um, die sich an der Informationshierarchie der Dictate-App aus dem Video orientiert:
- große Statusanzeige (Ready / Listening / Transcribing / Error)
- eine Zeile Kontext (Mode, Hotkey, Model)
- sichtbare letzte Transkription
- ein klarer Settings-Dialog
- CPU als echte, sichtbare und ehrliche Wahl
- alle bestehenden SonaBar-Funktionen bleiben erhalten und über "Open workspace" erreichbar

Das ist ein Shell-Rebuild, kein Logik-Rewrite. Keine bestehende Funktion still entfernen. Keine erfundenen Zustände, Modelle, Fortschritte, GPU-Fähigkeiten oder Threads.

# AUSGANGSLAGE (verifizieren, nicht raten)
- .NET 10 / WPF, Windows x64, Version 0.1.3.
- Engines: Whisper (whisper.cpp v1.9.4, CPU/GPU), Parakeet TDT 0.6B v3 (NeMo-Speech.cpp C ABI, CPU-only, 25 Sprachen, q8 GGUF), Qwen3-ASR (authentifizierter Named-Pipe-Sidecar, kein Netzwerk-Listener).
- Aktuelle Settings: Backend = "Automatic" | "CPU" | "GPU / accelerated"; Parakeet ist in ParakeetEngine.cs hart auf Gpu = -1; Whisper nutzt RecognitionThreadCount(Environment.ProcessorCount) = clamp(ProcessorCount - 1, 1, 16).
- Aktuelle UI: MainWindow.cs, ca. 1080x780, 6 Tabs + Subnav, Hero, Footer; Backend liegt unter Recording > Advanced; Models auf eigener Seite.
- Tests: 223/223; Package-Smoke 20/20. Build: ./build.ps1 -Configuration Release. Native Smoke: tests/SonaBar.NativeSmoke.

# NICHT ZU TUN
- Kein neues Python/Electron für die App; der bestehende Qwen-ASR-Sidecar bleibt unverändert. Kein Cloud-Zwang, keine API-Keys.
- Keine WhisperBar-Assets, keine WhisperBar-Edition, keine Affiliations-Behauptung.
- Keine Modellgewichte committen. Keine Downloads ohne HTTPS, SHA-256 und Lizenz.
- Keine Fake-UI: kein "GPU", wenn die Engine CPU-only ist; keine Threads, die nicht gesetzt werden; kein "Ready", wenn kein Modell geladen ist.
- Keine bestehenden Features entfernen: Files, Meetings, History, Statistics, Snippets (inkl. opt-in Typed Expansion), Writing, Custom Words, Applications, Privacy, Help, Updates, Themes.
- Qwen-ASR bleibt im authentifizierten Windows-Named-Pipe-Sidecar ohne Netzwerk-Listener.
- Exakten Roblox-String "Paste sent — check the app/target" nicht verändern.
- Version 0.1.3 nicht eigenmächtig bumpen; erst nach Abnahme.
- Keine Änderung an Default-Hotkeys oder bestehenden Settings ohne Migration.

# SOLL-UI
1. CompactWindow als Standardstart:
   - ca. 560-620 px breit, 600-720 px hoch, resizable, Min 520x560.
   - Titel "SonaBar"; Settings-Button; optional Tray.
   - Große Statuskarte: "Ready", "Listening…", "Transcribing…", "Could not insert", "Model not installed".
   - Metadatenzeile: Mode (Push-to-talk / Toggle), Hotkey, Model + effektives Backend (z. B. "Parakeet · CPU").

# DATEN & MIGRATION
- AppSettings.SchemaVersion auf 5 erhöhen.
- Neues Enum ProcessingDevice { Automatic, Cpu, Gpu }; CpuThreads int (0=Auto); MinHoldMs int (0-2000).
- Bestehendes Backend migrieren: "CPU" -> Cpu, "GPU / accelerated" -> Gpu, "Automatic" -> Automatic. Keine Werte verlieren.
- Validierung: CpuThreads 0..Environment.ProcessorCount (oder 1..64), MinHoldMs 0..2000; ungültige Werte auf Default.
- Settings-Tests für Migration, Clamp und Persistenz.

# ENGINE-/CPU-MATRIX
- Whisper: Automatic = CPU (schneller für kurze Diktate auf vielen Windows-Geräten); CPU = CPU; GPU = GPU mit sichtbarem Fallback auf CPU, wenn Laden fehlschlägt. Threads aus CpuThreads oder bisheriger Heuristik.
- Parakeet: CPU-only. GPU-Auswahl disabled mit Erklärung. Threads nur anbieten, wenn die NeMo-Speech.cpp-C-ABI/Runtime sie tatsächlich setzt; aktuell hat backend_config nur gpu. Wenn nicht: "Runtime default" read-only anzeigen, nicht faken. Effektiven Backend-Namen "Parakeet · CPU" anzeigen.
- Qwen ASR: CPU-only, Sidecar; keine GPU-/Thread-UI.
- Deutsches Parakeet (optional): nur nach Spike; siehe Modell-Abschnitt.
